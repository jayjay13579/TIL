
터미널 관련 복습

```sh
# 파일 move : mv + 무엇을 + 어디로
mv memo.md notes/

# 파일 copy : cp + 원본 + 복사본 으로 파일 복사
cp notes/memo.md plan.md

# 이름 바꾸기(별도 명령어 x) : mv + 원래 이름 + 새 이름
mv plan.md todo.md

# 파일 삭제 : rm, 휴지통 거치치 않고 삭제(복원 x)
pwd로 현재 위치 확인 > ls로 지울 이름 확인 > rm 지우기

# 폴더 삭제 : rm -r, 하위 파일까지 모두 삭제
rm -r notes

# 강제 전체 삭제 : rm -rf, -r 폴더 안까지 전부, -f 강제로 삭제(에러 무시)
rm -rf old


```

git 복습

- 버전 관리 시스템(VSC): 파일의 변경 이력을 기록해 여러 사람이 안전하게 협업하고,
문제가 생겼을 때 이전 상태로 되돌릴 수 있게 해줌.

- Git : 작업 내용을 커밋이라는 단위로 저장, 각 커밋은 특정 시점의 파일 상태를 보여 주는
스냅샷과 변경 정보를 담음. 그래서 누가 언제 무엇을 바꿨는지 확인하고, 필요한 버전으로 이동 가능
작업 디렉터리 변경 사항은 스테이징 영역을 거쳐 커밋, 필요한 변경만 골라 하나의 의도 단위 기록 가능
```

git diff : 작업 디렉터리와 스테이징 영역을 비교, git add한 변경 내용이 다음 커밋에 포함될
준비가 되었는지(-> 아무것도 안뜸) 확인할 때 유용. 수정했지만 아직 git add 하지 않은 내용 보여줌. 

git diff --staged : 스테이징 영역과 마지막 커밋(head) 사이의 변경사항을 보여줌

git add -p: 하나의 파일 내에서 서로 다른 목적을 가진 수정사항이 섞여 있을 때, 이를 분리하여 의도가 명확한 커밋으로 이력을 남김, 코드의 hunk(덩어리) 단위로 세밀하게 스테이징 여부 선택.
-> 한 커밋, 한 의도 원칙을 지키며 이력을 체계적으로 관리 가능

브랜치
- 파일 전체의 물리적 복사x, 특정 커밋 해시를 가리키는 40바이트 크기의 가벼운 포인터로 동작
- 하나의 저장소에서 작업을 목적별로 나누고 각 작업을 독립적인 흐름으로 관리
- 기능 개발, 버그 수정 등을 별도 브랜치에서 진행, 검토와 테스트 거쳐 메인 브랜치에 반영
-> 메인 브랜치의 안정성을 유지하며 기능별 개발과 협업을 안전하게 진행 가능

- feature/, fix/ 등의 브랜치 네이밍 컨벤션(명명 규칙)을 미리 정하면
브랜치의 목적을 한눈에 파악, 팀원 간의 혼란 줄이고 코드 리뷰와 병합과정 원활

- 깃허브 풀리퀘스트(PR) 생성 : 내가 작업한 변경 사항을 다른 브랜치에 합쳐 달라고 제안, PR을 만들면 어떤 코드가 바뀌었는지 확인하고, 다른 사람과 의견을 주고받거나 수정할 수 있음. 검토가 끝난 뒤 Merge를 하면 변경 사항이 main에 합쳐짐.

- rebase : 한 브랜치에서 만든 커밋들을 다른 기준점 위에 다시 올려놓는 작업


A ── B ── C  (main)
      \
       D ── E  (feature)

feature에서 main을 기준으로 rebase 하면 D,E의 변경 사항을 최신 main 뒤에
차례로 다시 적용

rebase 후:

A ── B ── C  (main)
           \
            D' ── E'  (feature)

이때 D', E'는 기존 커밋과 변경 내용은 비슷하지만 새로 만들어진 커밋
커밋이 이어진 기준점이 바뀌기 때문에 커밋 ID도 달라짐

*주의 : rebase는 커밋 해시를 새로 생성하여 히스토리를 재작성
따라서 원격에 푸시되어 다른 팀원과 공유된 브랜치(main, develop 등)에 Rebase를 적용하면, 기존에 해당 커밋을 기반으로 작업하던 팀원들의 히스토리와 엉켜 심각한 충돌이 발생. 이는 협업에 큰 지장을 주므로 공유 브랜치에서는 절대 금지.
- rebase 진행 중 충돌이 발생했을 때 해결 후 git add로 파일을 스테이징한 뒤 git rebase --continue를 입력하면 멈춰있던 다음 커밋들의 재적용 과정을 계속 진행

- 브랜치 전략은 기능 개발, 버그 수정처럼 서로 다른 작업을 분리해 안전하게 진행하기 위한 방법
- 각자 독립된 브랜치에서 작업하면 다른 사람의 작업에 영향을 덜 주면서 동시에 개발
-  작업이 끝난 뒤 브랜치를 병합하면 변경 사항을 관리하기 쉽고, 충돌도 줄일 수 있음

충돌
- 충돌은 서로 다른 브랜치에서 같은 파일의 같은 부분을 다르게 수정한 뒤 병합할 때 Git이 어떤 변경을 선택할지 판단하지 못해서 발생
- 먼저 충돌이 난 파일에서 충돌 표시를 확인하고, 남길 내용을 직접 수정, 그다음 충돌 표시를 제거하고 파일을 저장한 뒤 변경 사항을 스테이징하고 커밋하면 충돌이 해결됨
- git merge --abort : 병합(merge)을 시도했으나 충돌이 너무 복잡하게 얽혀 있어, 당장 병합을 포기하고 병합을 시도하기 전의 원래 상태로 완전히 되돌리고 싶을 때
